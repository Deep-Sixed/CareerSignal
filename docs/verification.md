## Limits

Job URL canonicalization collapses a single trailing separator, the default https port, a leading `www.` label, and an explicitly allowlisted set of tracking parameters (`utm_*`, `gclid`, `fbclid`, `msclkid`). Path case, repeated path separators, non-default ports, non-`www` subdomains and unlisted query parameters stay significant. Fragments are preserved except for a small set of in-page anchors, because hash-routed boards carry the job identity in the fragment; the earlier behaviour discarded every fragment and silently merged such jobs. Location eligibility compares a parsed work mode (`remote`, `hybrid`, `onsite`, or unstated) and region rather than raw strings, so `Remote`, `remote - US`, `US remote`, `fully remote` and `remote work` share one meaning while `remote US`, `remote Canada`, `hybrid` and `onsite` stay distinct. Region synonyms and the filler words dropped before a region is read are explicit allowlists; anything unlisted is kept as the literal place, so two places never merge. A posting whose work mode is unstated is never eligible, and a profile whose accepted locations state no work mode is rejected at construction rather than silently matching nothing. A work mode immediately preceded by a negation (`not remote`, `no remote`, `non-remote`) is excluded rather than offered, so an explicitly non-remote posting is never eligible for a remote profile; if that leaves another mode stated, that mode is used. A posting offering more than one unnegated work mode is recorded as ambiguous and is never eligible, because resolving it by the detection order would silently pick one meaning over another. A consequence worth knowing: `hybrid in office` states both `hybrid` and the onsite phrase `in office`, so it reads as ambiguous rather than hybrid. One deliberate allowance: a region-constrained profile still accepts a posting that states no region, and the review reasons record that the region was unstated. `Opportunity.location` keeps the raw normalized string, so this change does not move `Opportunity.key`.

Changing canonicalization changes `Opportunity.key`, so a database populated before this change keeps its old keys and will record a re-sent job under the new key as a separate opportunity. No backfill is performed.

After independent review 5134142759, the HTML parser was corrected to avoid hidden-state nesting for void elements and to promote only explicitly job-related links. Local regression coverage now totals 183 passing tests, including all supported void elements with hidden/aria-hidden attributes, nested hidden containers, navigation/footer links around valid jobs, supported apply-link text, and missing-URL rejection for unrelated links. A later pass addressed inline hidden styles: `display:none` and `visibility:hidden` on an element's own `style` attribute now conceal it, and a hidden container left unterminated at end of input is rejected as malformed rather than swallowing the remaining jobs. Regressions cover both, including that a non-hiding inline style stays visible and that malformed HTML leaves no partial intake.

Ruff, tree/privacy checks and secret detection pass. No historical source was inspected or copied for this feature.

This is a controlled application foundation, not completed live Gmail functionality. Inputs are structured synthetic jobs; scoring is a transparent configured skill ratio with a location eligibility gate. The caller records an explicit decision against an immutable review version. There is no web authentication layer or sending operation. The demo simulates the human decision step and labels its output accordingly.

The in-memory draft provider cannot recover its own state after process exit. A durable confirmed receipt replays safely; an attempt without a durable receipt remains uncertain and cannot be automatically retried. A future Gmail adapter must implement provider-specific reconciliation before claiming equivalent recovery. No personal data transfer or production mailbox validation was performed.
