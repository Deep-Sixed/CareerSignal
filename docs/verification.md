## Limits

Operator views are read-only queries over opportunities. One row is one opportunity, the durable business object, with the current review joined in as columns rather than becoming the subject of the list. Rows are ordered by pipeline stage, then coverage descending, then company and title; the stage order is the status vocabulary's own, so the sort happens in the application rather than in SQL. Filters cover a single status, the active set, eligibility in either direction and inclusive coverage bounds, and a filter that cannot mean anything stops the command instead of silently returning a different set. A table is printed by default because this is the first operator-facing view, and `--json` returns the same query result for anything that is not a person. The coverage column distinguishes a percentage, a job that stated no skills, a review that predates stated skill coverage and so is not actionable, and an opportunity with no current review; the last two would otherwise both read as blank. Nothing in this path records a status, decides a review, creates a draft or contacts a mailbox, which is asserted by snapshotting every table around every query command and by refusing to let a query construct a Gmail reader.

A test asserting that three quickly recorded events shared a timestamp raced for its own precondition rather than establishing it, and failed on a slow Windows runner mid-second; the tie is now written explicitly, with the same property also checked through the public API without any assumption about the clock. Mutating each history-ordering site separately then showed the detail view's ordering was untested, because no case made the two orderings disagree there.

These are the first commands to print externally sourced text to a terminal, and that boundary needed a guard. A job title originates in a recruiter's message and `clean` collapses whitespace without removing control characters, so `Engineer\x1b]0;spoofed\x07` reached storage intact and, printed raw, retitled the terminal window; `\x1b[2J` cleared the screen. Terminal-bound text is now escaped in `system/views.py` alone: C0, DEL and C1 characters render as visible `\x1b`-style text, so the operator sees that one was present rather than having it silently dropped. Stored evidence is untouched, because the record of what was actually sent must not be quietly rewritten, and ordinary Unicode is untouched too, because safety here is escaping control characters rather than restricting the alphabet. A newline inside an operator's reason stays structural, each line printed on its own row; only a line feed counts, with CRLF folded into it, because `str.splitlines()` also breaks on bare CR, VT, FF, FS, GS, RS, NEL and the Unicode line separators and would let a hostile control character vanish into structure instead of being escaped. `U+2028` and `U+2029` remain in the line unescaped, being outside the C0/C1 range and not terminal control sequences. The JSON form needs no treatment, since `json.dumps` escapes controls and must keep the underlying value for automation. Regressions run end to end from an ingested hostile opportunity through the CLI, cover every character in the control ranges, and cover nine sequences a real terminal would act on; each escaping site was mutated separately, after confirming each pattern matched exactly one line.

Two limits are worth knowing. There is no paging, colour or truncation, so a long title wraps rather than being cut, and presentation beyond that belongs to the operator interface. And sorting happens after the query returns, which is honest for a personal search and would need revisiting at a much larger scale.

An opportunity's status is the latest event in an append-only history rather than a column on the opportunity, so every state it passed through can be reconstructed and a correction never erases what preceded it. The vocabulary is fixed at nine values and a supplied status is normalized before storage; anything outside it is refused by the domain and, independently, by a SQL `CHECK`, with a test asserting the two lists cannot drift apart. No transition is forbidden, because a real search jumps between stages and there is no concrete rule to enforce yet. The current status is the latest row by id, not by timestamp: two events can share a second and a backfilled row can carry an earlier one, so ordering by the clock would reorder the history and can name the wrong current status. Nothing is deleted from the table, so ids stay monotonic. Every opportunity is opened at `new` at intake, by a write that inserts only when the opportunity has no history, which makes replay and a second message carrying the same job both no-ops. Recording a status writes nothing to any other table, creates no approval or draft intent, and calls no provider; migration 0004 backfills opportunities that predate the feature, naming `migration` as the actor so the row does not claim an operator was there.

Two limits are worth knowing. Concurrent recordings both persist -- append-only makes an overwrite impossible -- but nothing detects that the second operator was acting on a state the first had already changed; a compare-and-append guard would be a separate decision. And duplicate consecutive statuses are allowed, because recording one twice is what happened and collapsing it would be an edit.

The Gmail adapter is covered by generated invariants as well as named cases, for the reason the location suite was: three defects reached review in the adapter, and each was a claim in the documentation tested along the path that made the claim look true. The rules now stated over generated families are that every request is a GET carrying no body and addressing only the two allowlisted reads; that a duplicate listing entry never consumes the unique-message limit and every unique message offered within the page budget is returned; that no supplied access-token substring appears anywhere in a rendered exception chain; that mailbox intake never records an approval or draft intent or calls the provider; that the Gmail provider identifier decides provenance rather than the RFC822 `Message-ID`; that a mailbox differing only in case keeps one identity while a different mailbox never shares one; and that neither a malformed identifier, nor one Gmail itself returned, nor a constructed URL can address anything but an allowlisted read. The families total 733 cases, and one test asserts they are not silently empty.

Two properties of the suite are deliberate. Requests are intercepted at the opener rather than at the adapter's transport seam, so the real network helper runs and the method and body assertions describe the request the standard library would send; header validation inside that interception calls the standard library's own validator on an unconnected connection, so a rejection is the library's rather than an imitation of it and no socket is opened. An earlier draft reached for the real opener instead and spent thirty-five seconds attempting to dial Gmail, which would have put public CI on the network.

Building the families found two holes in them. Removing the URL-level reserved-segment guard and the echoed-identity check left every test passing, because families driven only through `fetch` cannot reach a second layer that the first layer always shadows, and families built from well-behaved payloads never make Gmail answer with the wrong identifier. Both gaps were closed by stating the same invariants over generated URLs and over mismatched responses. Review found a third hole, in the leak check rather than in a family: the rendered traceback was compared against one fixed token string that a third of the generated tokens did not contain, so those cases asserted nothing. Every generated token now carries a contiguous canary, the comparison covers the raw value, its repr-escaped spelling and its unicode-escaped spelling, and a companion test raises a deliberately leaking exception for every member of the family to prove the check can fail. A further test proves the check sees a chained cause and not a dropped one, which is the property `from None` exists to provide. Every guard in the adapter has since been removed one at a time and a named invariant confirmed to fail, fifteen for fifteen, including a helper that echoes the headers it was handed and a credentials error that repeats the value it rejected. That check is the only reason the two holes were visible at all: a green suite proves nothing about what it would notice.

Creating a draft in a mailbox is the first capability whose failure appears in somebody's inbox rather than on a terminal, so the guarantee is placed where it can hold. The Gmail compose scope is not a draft-only grant -- Google's definition of `gmail.compose` also permits sending -- so a scope string cannot be the guarantee and is not treated as one. The compose adapter is a separate module with a separate credential, a separate environment variable and a separate path allowlist; it defines no send method, and its allowlist refuses `users/me/drafts/send`, which is the Gmail send endpoint and matches the draft-path shape exactly. That single case is why the forbidden-segment list exists alongside the path pattern. The read adapter is unchanged and still refuses every scope but readonly, and `drafts` remains in its own reserved list, so neither credential reaches the other's endpoints.

An approval now binds to what was read: the review's content digest, the exact approved wording, and the status event that was current. All three are rechecked inside the transaction that reserves the write. A changed review or changed wording invalidates the approval absolutely; a status change invalidates it only into `rejected`, `withdrawn` or `closed`, because moving from `interested` to `applied` does not make the approved words wrong. Approvals recorded before this migration carry no binding and are refused rather than backfilled, since nothing records what they were for. The check and the claim share one `BEGIN IMMEDIATE`, so no event can be appended between them; the external request necessarily happens after the commit, so the event id observed by the check is recorded on the intent, which makes a later event a reconcilable record rather than a silent inconsistency. A refusal does not consume the approval: ending an opportunity refuses the draft, and recording an active status again makes the same approval usable.

The recruiter's `From` header becomes a message recipient, so a `CR` or `LF` in it splits the header and can add a reader. Such a value is refused and never repaired, without echoing the attempt. Three findings from building this are recorded because each was a place where the standard library's behaviour was nearly mistaken for a guarantee. `email.utils.parseaddr` passes a NUL straight through into the address it returns, so the raw value is scanned for control characters before parsing rather than after. More seriously, `parseaddr` does not fail closed on every supported interpreter: on CPython 3.11.9, which is what hosted CI installs for the 3.11 jobs and is inside the supported range, it returns the first address of a list instead of refusing it, so a recruiter `From` naming two mailboxes was accepted and silently reduced to one -- sanitizing a hostile value into an accepted one, which is the behaviour this boundary exists to prevent. Local runs could not see it because the local interpreter was newer than CI's, which is the same shape as a claim tested only along the path that makes it look true. Mailboxes are now counted with `getaddresses`, which agrees across every supported version and still reads a quoted comma inside a display name as a single address; the semicolon case is refused everywhere but for different reasons on different versions, so its test asserts the refusal and deliberately not the message. The control-character scan is what refused the CRLF case on 3.11.9, which is worth recording because mutation testing on a newer interpreter had reported that scan as redundant. And `compose` validates its own recipient and subject instead of trusting its caller, because a boundary that holds only while its one current caller sanitizes first is not a boundary; mutation testing found that gap by removing the caller's check and seeing nothing fail. The composed message is parsed back and checked to address exactly the intended recipient and to carry no `Cc`, `Bcc`, `Reply-To`, `Return-Path` or `Sender`, and those checks have their own direct tests because composition's own validation makes them unreachable through the public path. Stored evidence is untouched: the hostile header stays in `message_sources` byte for byte, asserted as the premise the other tests depend on.

Review of the first two commits found that a refusal was being recorded as an uncertain external write. The durable draft intent was reserved before the provider validated headers, so a refusal raised before any request reached the same handler as a failure after one, and the intent was marked uncertain. That state strands the review: an intent locks the decision for reconciliation, and reconciliation cannot find a draft that was never created, so the operator held an approval they could not use with no route back except editing the database. The test written alongside it asserted that state as though it were correct, which is the same failure this project keeps finding -- a claim tested along the path that made it look true. The provider is now asked whether the draft can be composed before anything is reserved, so a refusal leaves nothing to unwind rather than something to release; it records an audit event and no intent, and the approval survives. Everything past the request keeps the uncertain behaviour unchanged, because past that point the outcome genuinely is unknown. The refusal check runs the real composition and reports what it raised rather than repeating the rules, since two implementations of one rule drift the first time only one is corrected.

Proving the recovery path then exposed a second defect beside it. An opportunity can arrive in more than one message and replay reuses the review when the job has not changed, so a review can have several sources; the draft's recipient was selected by ordering on message id, which is a hash, so it was chosen arbitrarily and re-ingesting a corrected message might or might not take effect. The most recently ingested source now addresses the draft, ordered by the row the insert assigned, for the same reason status history orders by id rather than by a timestamp.

A 64-character intent key exceeds the header line limit and folds onto a continuation line, which reparses carrying the whitespace folding inserted. Both the composition check and the reconciliation comparison undo that folding. Without it reconciliation would have matched nothing, silently and permanently, which is the same class of defect as a documented claim tested along the path that makes it look true. Every guard added here was removed one at a time with a named test confirmed to fail, twenty-seven for twenty-seven, after checking each pattern matched exactly one site; four early misses were real and each was a gap rather than a nuisance -- an unasserted refusal reason, two unreachable verifier branches, and one line whose removal changed nothing, which was deleted rather than tested.

Two limits are worth knowing. The compose scope is configured, not verified, which is precisely why the adapter carries the guarantee. And reconciliation reads a bounded window of drafts, beyond which the answer is unknown rather than wrong.

Location parsing is covered by generated invariants as well as by named cases. The hand-written list can only contain what someone thought of, and every location defect found so far sat outside it, so `test_location_invariants.py` states rules that must hold across a whole generated family: an excluded region is never accepted by a profile configured for it and never becomes the positive region; a denied sole work mode is never eligible and never infers another mode; adding a denial never makes a posting newly eligible for any profile and never introduces a mode that was not there; a denial on one mode never removes another that is offered; and more than one offered mode is never eligible for any single-mode profile. Generation is deterministic and uses only the standard library, so a failure names one exact posting and reproduces immediately. A sixth rule was added after review: a denial covers every spelling of the mode it denies, and two spellings of one mode are that mode rather than an ambiguous pair. The families total 5,658 postings built from mode spellings, region spellings, denial and exclusion templates and joiners; one test asserts the families are not silently empty, since an empty family would make every invariant pass without testing anything.

That suite found a defect on its first run, in 174 of its cases. A denial whose availability word precedes the mode it names, as in `onsite, no option for hybrid`, was attributed to the earlier mode: the forward scan from `onsite` reached `option` and negated the very mode the posting offers, so a plainly onsite job read as `unknown` and was eligible for nothing. Only word order separated it from `onsite only, no remote option`, which was already covered and always behaved correctly. Prefix denials are now resolved first, because a negation reaching a mode across filler belongs to that mode and cannot also deny an earlier one. Three of the generated postings are also pinned in the named list so the finding stays readable without running the generator.

Review then found a second defect that the generated families had missed for the same reason the named list missed the first: they never placed two spellings of one canonical mode in a single posting. `no remote/WFH option` states one mode twice and denies it once; the denial attached to the first spelling, and the second re-offered the mode, so a posting that says it is not remote was eligible for a remote profile. That is a false positive, worse than the false negative above. Denial is now attributed to the canonical mode rather than to one occurrence of it, so a denied mode cannot be re-offered by another of its names, while two spellings of one mode still read as that mode rather than as an ambiguous pair. The generated family was extended to 960 same-mode denial postings and 160 same-mode offered postings, and four named regressions were added. The lesson is recorded because it generalizes: a generator only contains what its author imagined, exactly like a hand-written list.

Gmail intake is read-only by construction rather than by policy: `communications/gmail.py` defines no send, draft, label or modify operation, and the single network helper fixes its method to `GET`. Two URLs are addressable, both on `gmail.googleapis.com`; the guard refuses a different or look-alike host, plain HTTP, a non-default port, userinfo in the URL, any path outside the allowlist, and any final path segment naming a Gmail operation rather than a message. Message identifiers are validated against the same reserved list before a request is built, so neither a malformed identifier nor one Gmail itself returned can be spelled into a mutation URL. Redirects are refused, because following one would re-send the bearer token to the host the response named. The token is read from `CAREERSIGNAL_GMAIL_TOKEN` rather than a flag, travels only in an `Authorization` header, is absent from every error message, and is redacted from the credentials representation. Because a token is only ever used as a header value, one that could not legally sit in a header is refused at construction rather than trimmed: the standard library rejects such a value by quoting the entire header, which would place the token in a traceback, and silently trimming would authenticate with a credential the operator did not supply. The offending value is never echoed. The network helper independently converts that rejection into an error that drops the original cause rather than chaining it, since a chained cause is still printed. Each of these guards was verified by removing it and confirming a specific test fails.

Two honest limits on that claim. The configured scope is refused unless it is exactly `gmail.readonly`, but this constrains what CareerSignal asks for and does not inspect the token it is handed; the guarantee that nothing is written rests on the absent write path. And every Gmail test drives recorded synthetic payloads through an injected transport: they establish the adapter's contract, refusals and replay behaviour, not that Google's live API behaves as recorded. No personal mailbox has been read, and public CI never contacts one.

Provenance is the Gmail message identifier, never the RFC822 `Message-ID` header, which is written by the sender and can be shared by two different messages. The namespace is `gmail:<mailbox>` with the mailbox case-folded, so two spellings of one mailbox do not split a message into two identities; changing the mailbox string changes every message key derived from it. Reading the same mailbox twice returns the existing review references and writes no new message, opportunity, review or draft intent, and a provider identifier reappearing with different content is refused rather than overwriting evidence. Intake creates no draft intent and calls no provider. No write transaction is held open across a mailbox read, which is asserted by a test that opens a second writer during the read rather than only by inspection.

Message-level failures are all-or-nothing: one unreadable message stops the batch, matching the existing envelope rule that a body which cannot be parsed is not a message. Per-item independence applies to jobs inside a message, not to messages inside a mailbox. There is no incremental history sync and no retry or backoff; a 429 or 5xx is reported rather than silently repeated. A read limit counts unique identifiers rather than raw listing entries: a mailbox is not a snapshot, so the same identifier can appear on two pages, and letting a repeat spend the budget would silently under-read the mailbox by dropping a distinct message that was still to come. Paging continues past duplicates until the limit is met in unique identifiers, the pages run out, or the page bound is reached.

The fit score is job-relative: matched stated skills over total stated skills. The earlier formula divided by the configured profile size, which answered how much of the profile a job mentioned rather than how much of the job the profile covers, so a job stating thirty-two skills scored 100 when two matched. Extra configured skills no longer change coverage; profile relevance is retained as a separate diagnostic and takes no part in advancement. A job that states no skills is unscored rather than perfectly covered, and never advances. Because CareerSignal cannot yet distinguish required, preferred and merely mentioned skills, the measure is called stated skill coverage rather than a percentage of requirements met. The threshold and its strict comparison are unchanged at 70. Migration 0003 records the coverage components; `coverage` is NULL exactly when the job stated no skills. The legacy `reviews.score` column is NOT NULL and cannot be relaxed while foreign keys are enforced, because rebuilding `reviews` would break the provenance and decisions references, so it mirrors coverage and holds 0 for an unscored review; `coverage` and the stored payload are authoritative.

Upgrading an existing database does not recompute old reviews. A review written before this change carries an `advances` flag decided by the superseded formula, and migration cannot rescore it because the profile it was scored against is not recorded. Those rows keep NULL in all three new columns, and that NULL is the marker: the repository refuses to approve, reject or draft such a review rather than honouring a decision the current rules would not make, and the recorded reasoning is left untouched rather than rewritten to look as though it had been scored under coverage. A scoring-v2 review of a job that stated no skills stays distinguishable, recording `stated_skills` 0 with only `coverage` NULL.

To make a pre-v2 review actionable, re-ingest its opportunity under a new message ID. Replaying the original message does not rescore it, because an already recorded message returns its existing references unchanged; re-evaluation has always required a new intake event. The new intake scores the job under coverage, and the resulting review becomes the opportunity's current one, at which point the legacy review is stale by the existing rule.

Structured JSON intake now records a disposition for every supplied record rather than aborting the message on the first malformed one, matching the per-item behaviour the email path already had and the build contract's requirement that each opportunity be extracted independently. A record that cannot be normalized is stored as a rejected extraction item with its reason and creates no opportunity or review; valid siblings are unaffected. The distinction that remains all-or-nothing is the envelope: a body that is not JSON, or carries no nonempty `jobs` array, is unreadable as a message and fails before any database write. Conflicting versions of one job URL reject every conflicting record and leave the rest, using the same rule as the email path. Extraction excerpts can contain personal information at runtime for this path as well as for email; keep the database private and use synthetic fixtures in public tests.

Job URL canonicalization collapses a single trailing separator, the default https port, a leading `www.` label, and an explicitly allowlisted set of tracking parameters (`utm_*`, `gclid`, `fbclid`, `msclkid`). Path case, repeated path separators, non-default ports, non-`www` subdomains and unlisted query parameters stay significant. Fragments are preserved except for a small set of in-page anchors, because hash-routed boards carry the job identity in the fragment; the earlier behaviour discarded every fragment and silently merged such jobs. Location eligibility compares a parsed work mode (`remote`, `hybrid`, `onsite`, or unstated) and region rather than raw strings, so `Remote`, `remote - US`, `US remote`, `fully remote` and `remote work` share one meaning while `remote US`, `remote Canada`, `hybrid` and `onsite` stay distinct. Region synonyms and the filler words dropped before a region is read are explicit allowlists; anything unlisted is kept as the literal place, so two places never merge. A posting whose work mode is unstated is never eligible, and a profile whose accepted locations state no work mode is rejected at construction rather than silently matching nothing. A work mode denied by a negation is excluded rather than offered. The denial may precede the mode (`not remote`, `no option for remote`) or follow it (`remote not available`, `remote is not available`, `remote unavailable`), across intervening filler in either direction. A negation following the mode counts only when an availability word is near it, so `remote, not Canada` denies a region and leaves the mode offered. A denied region is recorded as an exclusion rather than folded into the positive region, so it can never read as a claim to be there: an unconstrained `remote` profile still accepts `remote, not Canada`, while a `remote Canada` profile rejects it, and no other region is invented in its place. A profile cannot itself be configured with an excluded region, since eligibility reads exclusions from the posting; and a denial never reaches across another stated mode, so in `onsite (no remote option)` the denial belongs to remote and onsite stays offered. A denial never infers the opposite mode, so an explicitly non-remote posting is never eligible for a remote profile; if that leaves another mode stated, that mode is used. A posting offering more than one unnegated work mode is recorded as ambiguous and is never eligible, because resolving it by the detection order would silently pick one meaning over another. A consequence worth knowing: `hybrid in office` states both `hybrid` and the onsite phrase `in office`, so it reads as ambiguous rather than hybrid. One deliberate allowance: a region-constrained profile still accepts a posting that states no region, and the review reasons record that the region was unstated. `Opportunity.location` keeps the raw normalized string, so this change does not move `Opportunity.key`.

Changing canonicalization changes `Opportunity.key`, so a database populated before this change keeps its old keys and will record a re-sent job under the new key as a separate opportunity. No backfill is performed.

After independent review 5134142759, the HTML parser was corrected to avoid hidden-state nesting for void elements and to promote only explicitly job-related links. Local regression coverage now totals 659 passing tests, including all supported void elements with hidden/aria-hidden attributes, nested hidden containers, navigation/footer links around valid jobs, supported apply-link text, and missing-URL rejection for unrelated links. A later pass addressed inline hidden styles: `display:none` and `visibility:hidden` on an element's own `style` attribute now conceal it, and a hidden container left unterminated at end of input is rejected as malformed rather than swallowing the remaining jobs. Regressions cover both, including that a non-hiding inline style stays visible and that malformed HTML leaves no partial intake.

This is a controlled application foundation. Inputs are structured JSON jobs, supplied text/HTML and RFC email, and messages read from an authorized Gmail mailbox; the Gmail path is verified against recorded synthetic payloads only, so live provider behaviour remains unestablished, and there is still no draft-write or send path of any kind. Scoring is stated skill coverage -- the share of the skills a job states that the configured profile matches -- with a location eligibility gate. The caller records an explicit decision against an immutable review version. There is no web authentication layer or sending operation. The demo simulates the human decision step and labels its output accordingly.

The in-memory draft provider cannot recover its own state after process exit. A durable confirmed receipt replays safely; an attempt without a durable receipt remains uncertain and cannot be automatically retried. The Gmail draft adapter implements provider-specific reconciliation by carrying CareerSignal's own intent key on the draft and matching on it, rather than guessing which draft was probably ours; ambiguity and an exhausted read window both report unknown rather than a receipt. No personal data transfer or production mailbox validation was performed.
