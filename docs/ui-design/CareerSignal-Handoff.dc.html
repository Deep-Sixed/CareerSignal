2

Minimal new read projections

Four functions and one derivation. All read-only, all on Repository beside the ones they extend, all expressible in the existing SQL vocabulary.

queue(summary, action) -> str          # pure function, module-level beside views
  "reconcile" if action["draft"] in ("attempting","uncertain")
  "created"   if action["draft"] == "confirmed"
  "stale"     if decision=="approved" and not binds and not attempted
  "draft"     if decision=="approved" and binds and not attempted and status not in TERMINAL
  "decide"    if advances and actionable and decision is None and status not in TERMINAL
  "rejected"  if decision=="rejected"
  "none"      otherwise                # includes pre-coverage, below-threshold, terminal
  Order of tests matters and mirrors _action's own precedence (an intent wins absolutely).

Repository.communications() -> list[dict]
  message_sources LEFT JOIN extraction_items, one row per message:
  {message_id, namespace, external_id, sender, subject, format, parser_version,
   extracted, unextracted, arrival}      # arrival = message_sources.rowid

Repository.communication(message_id) -> dict
  the row above + items=extraction_evidence(message_id)
                + addresses=[opportunity ids whose newest provenance row is this message]

Repository.sources(opportunity_id) -> list[dict]
  provenance JOIN message_sources WHERE opportunity_id=? ORDER BY p.rowid
  (the last element is the one _addressing() binds)

Repository.timeline(*, limit=200, since=None) -> list[dict]
  SELECT created_at, 'status', opportunity_id, NULL, status, actor, reason, id
    FROM opportunity_status_history
  UNION ALL
  SELECT a.created_at, 'audit', r.opportunity_id, a.review_id, a.event, NULL, NULL, a.id
    FROM audit a JOIN reviews r ON r.id=a.review_id
  ORDER BY created_at DESC, id DESC LIMIT ?

Not needed after re-reading the source: a digest projection (authorization() already returns everything the approve dialog shows and echoes) and any change to _summary, _action, _bound or opportunity(). The UI consumes those unchanged.

The one write-side change

Repository.decide(review_id, *, approved, actor, provider="controlled",
                  provider_namespace="controlled", expected=None)

  expected = {"content_digest","draft_digest","addressing_digest","status_event_id"}
  Inside the existing transaction, after binding = self._binding(conn, review_id)
  and before the upsert:
      if expected is not None and (
          expected["content_digest"]   != binding["content_digest"] or
          expected["draft_digest"]     != binding["draft_digest"] or
          expected["addressing_digest"]!= binding["addressing"]["digest"] or
          expected["status_event_id"]  != binding["status_event_id"]):
          raise BindingConflict(expected, binding)      # subclass of ValueError

  Optional, exactly as record_status's expected_event_id is optional and for the same
  stated reason: intake has no prior state to have moved; every operator-facing surface
  supplies it. The web layer always does. The CLI gains --expect on `approve` for parity.
  Compared inside the transaction, never before it — moving the check earlier only moves
  the race earlier, the argument record_status already documents.

Rejections send no expected: a rejection binds nothing, and requiring a fresh packet to record one would block the safest action behind the riskiest precondition.

4

Three architecture questions, answered by the contract

Does the design justify splitting Workflow? — Yes, and it is now the cheapest moment.

Workflow.__init__(repository, provider, profile) forces every caller to hold all three. The UI's two lanes need exactly one each: intake needs the profile and no provider; draft and reconcile need a per-request provider and no profile — and the Profile(("placeholder",)) in the draft path exists only because that is not expressible today. Under a web surface the placeholder gets worse, because a per-request provider means constructing a Workflow per request and inventing a profile each time.

Intake(repository, profile)           .intake_message(message) .intake(message_id, body)
OutwardActions(repository, provider)  .draft(review_id) .reconcile(review_id)

Pure motion: the method bodies are unchanged, the split is along the dependency they already use. test_operator_interface's no-second-route assertion re-points to OutwardActions. Land it before the web module so the web module never learns the placeholder.

Must careersignal.* namespacing precede the web work? — No, and it must not gate it.

The two are independent: namespacing is a mechanical rename of top-level packages (data, system, recruiting, communications), and the web module adds one subpackage plus a static resource directory under whichever name is current. The ordering argument is only about rename cost: doing it after the web module means a slightly larger diff, doing it before means the web PRs start on the final names. Neither is a correctness concern, and neither touches the wheel contract.

Where it does become a precondition: if the optional careersignal[web] extra is ever chosen (option B in the review), the extra's name and its import boundary should be expressed against a real careersignal namespace rather than a bare system.web — an extra that installs top-level system is a name-collision hazard in any environment that installs anything else. So: stdlib-only v1 → rename optional and independent; adopting a web extra → rename first. That is the actual dependency between the two open findings, and it argues for doing the rename before, not after, if a web extra is considered likely.

Connection and write model — unchanged from the review, restated as the implementation rule.

  • One connection per request, opened and closed on the handling thread through store.connection(); check_same_thread=True stays; nothing pooled or shared.
  • One in-process write authority with two lanes — local (status, decide, intake) and outward (draft, reconcile) — so a 30 s Gmail call cannot block a status append. The lock is for UX; every invariant remains enforced inside BEGIN IMMEDIATE.
  • One HTTP request = one engine call = one transaction. No transaction spans a response or a network call.
  • The CLI may write concurrently; it can only lose a race loudly. Reservation exhaustion surfaces as a REFUSED-shaped banner ("another writer held the database; nothing was written").
