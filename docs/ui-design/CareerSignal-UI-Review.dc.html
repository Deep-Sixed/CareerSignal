What the engine actually is (read from the code)

Everything below is derived from src/data/repository.py, src/system/workflow.py, src/system/views.py, src/system/cli.py, the seven migrations and the docs. The UI has four kinds of thing to show, and it already has the projections for three of them.

ConceptWhere it livesUI consequence
Opportunityopportunities + Repository.SUMMARY/_summary(); status derived from opportunity_status_history (latest by id)The durable business object. One row per opportunity everywhere; the review is columns, not the subject.
Review / fit evidencereviews (payload with reasons, coverage, eligible, advances); scored/actionable flags for pre-coverage rowsShown inside the opportunity. Never its own list.
Recruiting communicationmessages, message_sources, extraction_items, provenanceRead-only evidence. No body is stored — only excerpts. No timestamp column exists (see §8).

The UI must show exactly _bound() and echo _binding()'s digests back on approve.

Four outcomes already name every result an action can have — ACCEPTED, REFUSED, PROVIDER_REJECTED, UNCERTAIN (plus exit-2 misuse). The UI adopts that vocabulary verbatim rather than inventing toasts.

Information architecture

Primary navigation (five items, all views over one state)

Dashboard
Counts by status + work queues derived from _action()
Inbox
message_sources → extraction_items → linked opportunities
Opportunities
opportunities() with the CLI's filters
Approvals
Same rows, filtered to reviews that advance; ordered by urgency
Activity
status history ∪ audit, newest first

List / detail relationships

  • One detail pane, two shapes. Dashboard, Opportunities, Approvals and Activity all select an opportunity and show OpportunityDetail. Inbox selects a message and shows CommunicationDetail. Activity can select either (a status/audit event → opportunity; a message event → message).
  • Approvals is a filter, not a screen of its own. Its list is opportunities() rows where the current review is actionable and advances, sorted: reconcile → stale → awaiting decision → ready to draft → created → rejected. Selecting one opens the same OpportunityDetail, scrolled to the packet.
  • Cross-links follow provenance. Opportunity detail lists the messages that carried it (provenance, newest wins for addressing); message detail links each extracted item to its opportunity (extraction_items.opportunity_id).
  • Which concepts belong together. Opportunity ⟷ review ⟷ approval ⟷ draft are one object in the UI because the engine binds them as one (_binding() reads them in one statement). Messages stay separate because they are evidence about many opportunities and are never edited.

Deliberately not in v1 navigation

Contacts would need new backend scope: a contacts table keyed on a normalised address, a sender→contact link, and a rule for what to do when a recruiter's display name changes — plus a decision about whether it may ever influence addressing (it must not; _addressing() stays the only source). Tasks would need a table with its own append-only history and a due-date model. Neither is required to be "substantially easier than the CLI", so both are deferred (§6).

Screen-level specification

Dashboard

  • Purpose. Answer "what needs me" in one glance and route to it.
  • Data. Count per status (9 cells). Queues: needs reconciliation (draft ∈ {attempting, uncertain}); stale approvals (decision=approved ∧ ¬binds ∧ ¬attempted); awaiting decision (advances ∧ actionable ∧ decision=null ∧ status ∉ TERMINAL); ready to draft (approved ∧ binds ∧ ¬attempted, including after draft_rejected); items not extracted; new and untouched. Session facts: db path, SQLite version and WAL-fix flag from sqlite_report(), which tokens are present (never their values), declared mailbox.
  • Actions. Ingest (.eml upload; Gmail read if configured). Each queue row navigates.
  • Empty state. "No opportunities yet — ingest a message." with the ingest control in place.
  • Warnings. Reconcile and stale queues render in the deep accent step; SQLite below the WAL-fix range shows the diagnostic line version already prints.

Inbox

  • Purpose. See what arrived and what the extractor did with it. Evidence, not mail.
  • Data. List: sender, subject, namespace, format, extracted / not-extracted counts. Detail: external id, parser version, every extraction_items row with excerpt and reason, link to the opportunity (and whether the linked review is still that opportunity's current review).
  • Filters. Namespace; "has unextracted items"; free text over sender/subject. A "by sender" grouping is the Contacts substitute.
  • Actions. None that write. "Open opportunity" only.
  • Empty state. "Nothing ingested yet."
  • Warnings. Sender/subject are recruiter-controlled: rendered with textContent and control characters shown as \x1b-style glyphs (the browser twin of views.safe). A banner states that evidence is never edited; corrections are a new message id.

Opportunities

  • Purpose. The CRM list. Same rows and order as careersignal opportunities.
  • Data. Row: company, title, status tag, coverage as spelled by views.coverage(), queue tag from _action(), time since last status event. Detail: header tags (status, event id, coverage, eligible, advances), URL, review evidence, approval packet, action state ("where it stands as an action": the exact views.approval() / views.attempt() sentences), history table, provenance, audit events.
  • Filters. Exactly the CLI's: single status, active, eligible/ineligible, min/max coverage, plus client-side text search. Invalid combinations are impossible by construction (segmented controls), so exit-2 errors have no UI equivalent.
  • Actions. Change status (always). Approve / Reject (when actionable ∧ advances ∧ ¬attempted ∧ status ∉ TERMINAL). Create draft (when approval binds, no intent, status not terminal). Reconcile (when intent is attempting/uncertain). Buttons hidden when the rules would refuse, with the refusal reason shown as text instead — but the server still refuses independently.
  • Empty state. "No opportunities match." mirroring views.table().
  • Warnings / refusal states. Pre-coverage review: "not actionable; re-ingest under a new message id". Structured intake with no message: "no recipient — a draft would be refused". Terminal status: "an ended opportunity authorizes no outward draft". Stale approval: the three remediations verbatim.

Approvals

  • Purpose. The work queue for the only thing that leaves the machine.
  • Data. Opportunity rows with a queue tag; detail is the same OpportunityDetail, packet first. The approve dialog shows recipient, subject, wording, the content/draft/addressing digests and status event it will carry, destination select, actor.
  • Filters. Queue (reconcile / stale / awaiting / ready / created / rejected); destination.
  • Actions. Approve for a destination, reject, create draft, reconcile.
  • Empty state. "Nothing awaits a decision. Approvals appear when a review advances the threshold (strictly above 70)."
  • Refusal states. 409 from a stale packet: "This packet changed while you were reading it" with a diff of what moved (recipient / subject / wording / status) and a single "Reload packet" action. "Draft already attempted; decision is locked." shown in place of approve.

Activity

  • Purpose. "What happened while I was away", and an audit trail a person can read.
  • Data. Union of status events (event id, status, actor, reason) and audit events (review_created, approved, rejected, draft_intent, draft_confirmed, draft_uncertain, draft_refused, draft_rejected), each with the opportunity it concerns. Message arrivals appear only once a timestamp exists (§8).
  • Filters. Kind; actor; since.
  • Actions. Navigate only. There is no undo, no edit, no delete — the tables refuse them.
  • Empty state. "No activity recorded."

UI-facing application contract

Read models extend _summary(), _action(), _bound() and opportunity(). Nothing is renamed; the UI consumes the same JSON --json already emits, plus four additions marked new.

Read models

OpportunitySummary  = Repository._summary(row)               # unchanged: id, company, title, location, url,
                                                              # status, status_changed_at, review, coverage,
                                                              # matched_skills, stated_skills, advances, status_event,
                                                              # eligible, scored, actionable
                    + queue: "reconcile"|"stale"|"decide"|"draft"|"created"|"rejected"|"none"   # new, derived from _action()
                    + opened_at                                # new: created_at of the opening 'new' status event

OpportunityDetail   = Repository.opportunity()                # unchanged: ...summary, packet, action, bound, history[]
                    + binding: { content_digest, draft_digest, addressing_digest, status_event_id }   # new: subset of authorization()
                    + sources: [CommunicationSummary]         # new: provenance join, newest last
                    + audit: [ {event, created_at} ]           # new: audit(review_id) with timestamps

CommunicationSummary = message_sources row                    # message_id, namespace, external_id, sender, subject,
                                                              # format, parser_version
                    + extracted, unextracted (counts from extraction_items)

CommunicationDetail = CommunicationSummary
                    + items: Repository.extraction_evidence(message_id)   # index, excerpt, reason, opportunity_id, review_id
                    + current: per item, whether review_id == opportunities.current_review

TimelineEvent       = { at, kind: "status"|"audit", opportunity_id, review_id?, status?, actor?, reason?, event? }
                      # union of opportunity_status_history and audit, ordered by created_at desc then id desc

ApprovalSummary     = OpportunitySummary where actionable and (advances or decision exists)
                    + action: Repository._action()            # unchanged
                    + destination: {provider, provider_namespace}

Config              = { db_path, sqlite: sqlite_report(), providers: ["controlled","gmail"?],
                        declared_mailbox?, read_token_present: bool, compose_token_present: bool }   # never a token value

Commands (one HTTP request = one engine call = the engine's own transaction)

POST /api/opportunities/{id}/status
  { "to": "applied", "actor": "operator", "reason": "Sent CV", "expect_event": 12 }
  → 200 { outcome: "accepted", status, event, expected_event }
  → 409 { outcome: "refused", status, event, expected_event, message, next }      # StatusConflict

POST /api/reviews/{id}/decision
  { "approved": true, "actor": "operator", "provider": "gmail", "mailbox": "operator@example.com",
    "seen": { "content_digest": "…", "draft_digest": "…", "addressing_digest": "…", "status_event": 12 } }
  → 200 { outcome: "accepted", message }
  → 409 { outcome: "refused", message, changed: ["addressing"], current: binding }  # BindingConflict (new)
  → 200 { outcome: "refused", message }     # decide()'s own refusals: ineligible, terminal, locked, pre-coverage
  Rejection: { "approved": false, "actor": "…" } — no "seen" required; a rejection binds nothing.

POST /api/reviews/{id}/draft       { "provider": "gmail", "mailbox": "operator@example.com" }
POST /api/reviews/{id}/reconcile   { "provider": "gmail", "mailbox": "operator@example.com" }
  → 200 the exact record cli.attempted() builds: { outcome, state, receipt, message, next }
    HTTP status maps the outcome: accepted 200, refused 200, provider_rejected 200, uncertain 200 —
    the outcome field is the contract; HTTP codes are reserved for transport, 404 unknown id, 409 stale read, 400 malformed.

POST /api/intake/eml      multipart .eml + namespace          → { reviews, diagnostics }   (as cli ingest)
POST /api/intake/gmail    { label_ids, query, limit }         → { mailbox, read, messages } (as cli gmail-ingest)
  Profile (skills, locations, threshold) comes from server launch configuration in v1, exactly as the CLI takes --skill.

The one backend addition the contract needs

decide() today binds whatever is current at commit time. That is correct for a terminal that just printed the packet, but a browser page can be minutes old. The fix mirrors record_status's expected_event_id:

Repository.decide(review_id, *, approved, actor, provider, provider_namespace,
                  expected=None)   # {"content_digest","draft_digest","addressing_digest","status_event_id"}
  inside the BEGIN IMMEDIATE transaction, after _binding():
    if expected is not None and any(binding[k] != expected[k] ...): raise BindingConflict(changed=[...])

Optional, so intake and existing callers are untouched; the web surface always supplies it, as the CLI always supplies --expect. The check is inside the transaction because checking before it would only move the race earlier — the same reasoning the status path already documents. BindingConflict should subclass ValueError so existing refusal handling still refuses.

To render the packet the UI also needs the digests, which authorization() already computes; exposing them as OpportunityDetail.binding is a projection change, not a schema change. Approval remains bound to what the operator saw because the server compares what the page carried back against _binding() — the same statement _bound() rendered from.

First-release acceptance contract

Required for the first usable UI

  • Three-pane shell; Dashboard, Inbox, Opportunities, Approvals, Activity
  • Opportunity list with the CLI's filters and ordering
  • Opportunity detail = opportunity() rendered in full: evidence, packet, action state sentences, history, provenance
  • Change status with expect_event; 409 shown as the CLI's REFUSED
  • Approve/reject with digests carried back; decide(expected=…)
  • Create draft (controlled and Gmail); reconcile; the four outcomes as distinct banners
  • Inbox list + message detail with extraction items
  • Activity timeline from the two append-only tables
  • Ingest an .eml; trigger Gmail read when the token is present
  • Loopback bind, per-launch token, CSP, textContent rendering
  • Source test: web module has no route to a provider except Workflow

Desirable next

  • messages.received_at (or on message_sources) so Inbox and Activity can order by time
  • Persisted profile (skills, locations, threshold) with a Settings pane — new persistence, outside the DB or a small table
  • Inbox "by sender" grouping (derived, no schema)
  • Keyboard navigation j/k, "/" search
  • Stale-packet diff on 409 (which of recipient/subject/wording moved)
  • Follow-up hints: active opportunities with no event in N days (derived, no schema)
  • Bulk status change as N independent compare-and-appends with per-row outcomes

Explicitly deferred

  • Contacts as a first-class model (new table + normalisation rules)
  • Tasks / reminders subsystem
  • Editing draft wording in the UI — the wording is produced by evaluate() and bound by digest; editable drafts need a new review version path first
  • Multi-user, auth, remote access
  • OAuth flow / token storage — stays the operator's job
  • Reading message bodies — not stored, by design
  • Desktop packaging (§7)
  • Any sending, any application submission, any automatic action

Acceptance test, in one sentence: a job seeker can ingest a week of alerts, see which opportunities advance, decide each, create and reconcile a Gmail draft, and later read back exactly what happened — without typing a 64-character id once, and without any path the CLI does not already have.

Architecture recommendation

Web stack — three options against the zero-dependency contract

OptionForAgainst
A. stdlib-only — http.server.ThreadingHTTPServer, json, static HTML/JS served via importlib.resources (as migrations already are)Keeps dependencies = [] and verify_wheel.py untouched in all 12 cells. The surface is ~8 GETs and ~6 POSTs for one user on loopback; routing is a dict. Same packaging story as today: careersignal serve in the wheel.Hand-written request parsing, multipart for .eml upload (email.parser handles it), no async, no auto-docs. ~400–600 lines of careful code that must be tested like the CLI is.
B. optional extra careersignal[web] (e.g. a small ASGI stack)Core wheel stays dependency-free; better ergonomics for validation and static files.Two install shapes to certify; verify_wheel.py must prove the core still declares nothing while the extra installs cleanly; an import-boundary check must keep system.web from being imported by the CLI path. C. formal exception — a third-party web stack as a runtime dependencyOnly justified if the UI needs websockets, sessions, or a real templating layer.It does not. Breaks a contract that is enforced by CI and stated in the README.

Recommendation: A for v1, with the web surface under src/system/web/ (the build contract already places the operator UI under system). The frontend is static vanilla HTML/JS with the design tokens as CSS variables — no build step, so nothing new enters the wheel gate. Revisit B only if a later feature needs it; the API contract in §4 is stack-neutral so the move would be mechanical.

Desktop vs local web. A desktop shell (pywebview, Electron, Tauri) adds a dependency or a second toolchain and gives one user on one machine nothing the browser does not — no tray, no notifications are in scope. Ship local web: careersignal serve binds 127.0.0.1 on an ephemeral port, prints (and optionally opens) a URL carrying a per-launch random token. Desktop packaging is deferred.

SQLite connection model and writer serialisation

  • Connections. One per request, opened on the handling thread through the existing connection(), closed before the response is written. check_same_thread=True stays. No connection is ever cached, pooled, or shared across threads. Reads run in autocommit and are never blocked by a writer under WAL.
  • Write authority. One in-process WriteAuthority owned by the server: a lock (or one worker thread with a queue — equivalent here) through which every mutating command passes. Two lanes: local (status, decide, intake) and outward (draft, reconcile). Each lane executes one command at a time; the outward lane holds a Gmail call for up to 30 s and must not block a status change, so the lanes are separate. The database remains the final arbiter: every command still runs the engine's own BEGIN IMMEDIATE with its 20 ms busy timeout and bounded retry, so the lock is for UX — no spurious Write reservation exhausted from a double-click — not for correctness.
  • Request/transaction boundary. One HTTP request → one command → one Repository/Workflow call. No transaction spans a request, a response, or a network call (Workflow.draft already commits claim() before contacting Gmail). A request never holds a connection while waiting for the lock.
  • CLI concurrency. The CLI may keep writing while the server runs. This is stated rather than forbidden because every invariant that matters — compare-and-append, digest and destination binding, one intent row — is enforced inside the transaction, not by process ownership; a second process can only lose a race loudly, never silently. The UI handles TimeoutError from the reservation as a REFUSED-style banner ("another writer held the database; nothing was written; try again") and every 409 by re-reading. If a single authority is nevertheless wanted, the cheapest honest mechanism is a var/careersignal.db.serve lockfile the CLI's mutating commands check and refuse with exit 2 unless --allow-concurrent is given — a documented courtesy, not a guarantee, and not needed for v1.

Approval correctness across the browser round trip

Covered by §4: OpportunityDetail.binding out, seen back, compared inside decide()'s transaction; expect_event on status. Draft and reconcile carry only the declared destination because the approval row is the binding — claim() rechecks it. A stale page can therefore never approve or record something it did not display; it can only be refused.

Reference projects (patterns, not code, for v1)

The zero-dependency, no-build posture rules out copying components from React/Vue codebases into v1. Use them as interaction references: shadcn-admin for the shell (sidebar + list + detail, command search) and, if a build step is ever accepted, as the shell donor; chatwoot for the Inbox three-pane rhythm and the "context panel" idea the packet card follows; jobhunt for job-seeker pipeline vocabulary and column density; atomic-crm for activity/timeline and filter-sidebar patterns — its deals/Kanban model is not adopted. Licences (all believed permissive, MIT for the first, second and fourth) must be verified in the reuse ledger before any file is copied; jobhunt's licence in particular needs confirming.

What this decides about the open refactors

  • Workflow split — do it as part of the web work, because the web surface composes the halves separately. Intake needs a Profile and a reader; drafting needs a per-request provider and no profile. The UI contract makes that concrete: Intake(repository, profile) with intake()/intake_message(), and OutwardActions(repository, provider) with draft()/reconcile(). The Profile(("placeholder",)) disappears; the CLI is adjusted to the same two classes, and test_operator_interface's no-second-route assertion is re-pointed. Land this before the web module so the web module never learns the placeholder.
  • careersignal.* package move — independent; do not make it a prerequisite. The web module adds one package (system.web) and a static-resource directory. Renaming is mechanical either before or after; doing it first only makes sense if it is already committed for this milestone, because the web module doubles the import surface a later rename must touch. Recommended order: Workflow split → contract additions → web → rename (if still wanted).

Detail-pane rules settled in review

  • Reading order. What is this → where is it in my search → what needs my attention → why CareerSignal concluded this → what exactly I would authorize → what happened. Header, attention panel, primary action row, evidence + packet, action-state sentences, then a "History & evidence" divider before status history and provenance.
  • Attention panel (top of the pane, first-class): UNCERTAIN / attempting — steel field, "CareerSignal cannot prove whether Gmail created the draft. Do not retry until reconciled." with the only outward action, Reconcile. PROVIDER REJECTED — "Gmail rejected the request; nothing was created", offers Retry draft. REFUSED — "CareerSignal did not contact Gmail", offers nothing outward. APPROVAL STALE — "Your approval no longer matches the current material", offers Review changes (a before/now table of recipient, subject, wording, status) and Re-approve. Stale + attempted shows the outcome panel instead, because decide() is locked.
  • Three decision states, never "Approve again". Undecided → Approve / Reject. Approved and current → "✓ Approved by … for gmail:…" with Withdraw approval (only while no intent exists; it is decide(approved=False)). Stale → handled by the attention panel. Rejected → tag + Approve instead.
  • Create draft is always visible once a review advances, disabled with the reason beneath it ("Requires an approval for a destination", "Requires a current approval — re-approve above", "Opportunity has ended") rather than hidden or letting the click earn a refusal. The server refuses regardless.
  • Inbox detail order: sender, subject, tags → Extracted opportunities (cards with status, coverage, queue, and whether this message is still the current addressing source) → Stored evidence (per-item excerpts, reasons) → Provenance record (ids, namespace, raw sender/subject, format/parser, arrival order, which drafts it addresses). "Original message" is not a section because the body is not stored.
  • Demo mode. The mock's scenario controls (status conflict, draft outcome, reconcile outcome, full ids) are not product UI. Keep them as a --demo flag on careersignal serve that swaps in the controlled provider and scripted outcomes, so acceptance tests can drive REFUSED / PROVIDER_REJECTED / UNCERTAIN / stale-approval / stale-status without a mailbox.
